# Private identity collection, 14 October 2026

The user explicitly selected **store the dossier first; integrate eKYC later**. This slice provides collection, authenticated retrieval and replacement only. It does not implement Admin review, OCR, face matching, liveness, provider callbacks or legal verification. No identity documents leave this application.

`/account/settings` links to `/account/settings/identity`. The dedicated form collects legal name, twelve-digit Vietnamese citizen ID number, birth date, issue date and authority/place, address on the document, current living address, and both front/back JPEG or PNG images. These addresses are distinct; display profile name/address are not silently overwritten. Both images and all structured fields are required on first save. On update an omitted image retains its stored counterpart. Dates and field lengths are validated server-side; issue date cannot precede birth. This is not document authenticity validation.

`GET /api/v1/me/identity` returns 204 when absent. `PUT` takes multipart JSON `profile` plus optional `front` and `back` images. Creation requires a null/omitted version; update requires the current integer version. A locked account row serializes creation/update, and `@Version` detects outdated writes. Saving is atomic. Unknown metadata fields, including account IDs and verification flags, are rejected. All submissions remain `NOT_VERIFIED`; the UI says “Đã cung cấp hồ sơ · Chưa xác minh danh tính”. There is no public command that sets verification success.

V11 adds separate profile and binary-content tables keyed to the authenticated account. An image is decoded as PNG/JPEG, limited to 5 MB and 20 million pixels, and re-encoded before storage. Request limit is 11 MB to accommodate two 5 MB files plus metadata; the per-file limit remains 5 MB. Original file names and public URLs are not stored. Private image reads use Bearer authentication, no-store, nosniff and attachment headers; React displays short-lived object URLs and revokes them on cleanup. Neither Owner nor Admin has cross-account access in this slice. No identity fields are added to public apartment, account-menu or ordinary profile DTOs.

Contact possession and identity verification remain separate domains. `AccountVerificationPolicy` continues the implemented email requirement for Customer rental operations. Collecting identity evidence neither satisfies that policy nor changes account/email status, and cannot be used as an eKYC success signal. Requiring **email AND verified identity** is deferred until an actual verification method and its result lifecycle exist; otherwise everyone would be blocked by an unavailable method. No existing fixture is reset or automatically verified. Future provider integration should persist evidence-backed results for this identity revision and invalidate them on revision changes, then compose the rental eligibility policy without replacing email possession checks. Contract authoring integration/snapshots of these new fields are a separate change; existing contract drafts are preserved.

This is current-account storage, not immutable verification-submission history. Identity deletion/retention, provider configuration, legal identity review and controlled disclosure to the other contract party remain separate work. Existing property dossiers/review/approval are unaffected. RDS/diagrams are preserved; legacy claims that uploaded CCCD proves identity do not describe this implementation.

Framework research: Context7 Spring MVC multipart reference, checked against the installed Spring Boot 4.1.1 / Spring Framework 7 dependencies. No new framework dependency or provider SDK.
