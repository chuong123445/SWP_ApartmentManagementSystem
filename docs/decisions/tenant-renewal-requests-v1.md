# Tenant requests renewal before the next contract

Authorized 2 November 2026. Supersedes direct Owner-initiated renewal in the 28 October lifecycle implementation. No automatic renewal, release, payment or signature copying is introduced.

- Private in-app notices for both exact parties at 20 and 10 days before end date. Persistent unique contract/recipient/end-date/milestone keys; hourly job after an initial minute. On a missed run, generate the nearest current milestone (11–20 days: 20; 0–10: 10), avoiding two overdue reminders together. No email/SMS delivery is claimed.
- The exact ACTIVE, rental-verified tenant (including an OWNER renting another property) requests renewal on an ACTIVE contract, before or after its end date. A pending handover blocks it. One request record per contract, duplicate sends return that record. Rejected/cancelled requests remain terminal for this contract; a second negotiation is not implemented.
- Owner accepts or rejects the request using its optimistic version; rejection needs a reason. Acceptance does not sign/activate a new contract. Only an accepted request unlocks the existing authoring wizard. Owner can cancel acceptance before authoring, or cancel a successor that has not received both signatures. Preserve decision/time/reason and cancellation time. No unilateral cancellation of a fully signed future contract is provided.
- A renewed contract has fresh snapshot/content/hash and signatures; the predecessor remains readable. End-date overlap is rejected. Both signatures before the next start leave the successor DRAFT but SIGNED/read-only, shown as waiting for the next term. Its predecessor stays ACTIVE until the next term. On/after start date, a separate transactional activation service ends the predecessor with RENEWED and activates the successor, with the existing unique ACTIVE-apartment constraint. Missing meter readings stay missing; available predecessor last SENT readings/baselines carry forward. Draft invoices, rights/account problems or other conflicting contracts defer activation without releasing the apartment. No repair/reset/provider call occurs in the job.
- Owner may propose handover on/after end date only when no pending/accepted renewal request or open successor remains. Pending requests require an explicit decision, not a timeout rejection. Rejected/cancelled requests permit handover at expiry. Accepted requests must be explicitly cancelled if no successor exists, or the successor cancelled before both signatures. Tenant confirmation remains required to end the old contract and make the apartment VACANT.
- Commands serialize on the original accepted selection, then contract locks; request uniqueness and the existing renewal/ACTIVE constraints guard duplicates. Read APIs expose lifecycle request status/version and server-derived handoverAvailable to exact parties. No client account IDs, status flags, fees, signatures or publication flags grant access.

V42 adds `contract_renewal_requests` and `contract_expiry_notices`; both are additive, rerunnable SQL Server migrations. The job is disabled under profile test and can be disabled with `app.contract-lifecycle.scheduler-enabled=false`. Run isolated tests on the existing verified SQL clone, never reset `proptech_db` fixtures.

History UX: signed/ended agreements are view-only; expired ACTIVE relations say pending resolution. Rows open the exact contract route. If an old relation has no saved contract document, the UI can show only the summary returned by authorized tenancy APIs, explicitly explaining that original PDF/signatures are unavailable. Errors other than document 404 must remain errors; never manufacture a legacy document.
